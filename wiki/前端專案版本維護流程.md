# 前端專案版本維護流程

## Summary
- 觸發情境：前端專案 release、版本號更新、API_KEY 更新與打包部署。
- 參與角色：前端工程師、Ray；其他 reviewer、QA、release owner 待補。
- 產出物：版本號、API_KEY 對應、Merge Request、CI/CD 結果、deploy script 打包產物。

## Steps
1. `web-app` 舊流程使用 `config/version.js` 管理 API_KEY 更新；新功能發布時建立新的 API_KEY，並同步更新大 / 中版本號。
2. `web-app` 舊流程發布時切到 `deploy` branch，拉取 submodules 後執行 `./deploy_tool.sh 版本號`；香港版本使用 `hk_deploy` branch 與 `./deploy_tool_hk.sh 版本號`。
3. `web-app` 新流程由前端工程師負責 feature 或 bug，完成後發 MR。
4. Ray 核准後跑 CI/CD，版本控制由 Ray 管理。
5. `web-front` 版本號記錄於 `package.json`。
6. `web-front` 透過 `npm run version-update major [NEW-API-KEY]`、`minor` 或 `patch` 更新版本號，再執行 `sh deploy_tool.sh`。
7. `web-front` 只有大版本需要更新 API_KEY。
8. `web-front` 手動打包需排除 `_deploy` 與 `node_module`；使用 `deploy_tool.sh` 會自動排除。
9. `web-kit` 台灣版本使用 `master` branch，香港版本使用 `hk_version` branch；透過 `sh build_deploy.sh 版本號 -staging` 或 `sh build_deploy.sh 版本號` 打包。
10. `web-kit` 需要時使用 `sh deploy_latest.sh -staging` 或 `sh deploy_latest.sh` 將指定版本設定為 latest stable version。

## Project Rules

| 專案 | 版本位置或方式 | API_KEY 規則 | Branch / 地區 | 打包或部署指令 |
| --- | --- | --- | --- | --- |
| `web-app` | 舊流程使用 `config/version.js`；新流程由 Ray 管理版本控制 | 新功能發布會建立新的 API_KEY，並同步更新大 / 中版本號 | 台灣：`deploy`；香港：`hk_deploy` | `./deploy_tool.sh x.y.z`、`./deploy_tool_hk.sh x.y.z` |
| `web-front` | `package.json`，透過 `npm run version-update` 更新 | 僅大版本需更新 API_KEY | `master`、`staging`、`deploy`；建議 release branch 是否正式採用待補 | `sh deploy_tool.sh` |
| `web-kit` | 指令指定版本號 | 待補 | 台灣：`master`；香港：`hk_version` | `sh build_deploy.sh x.y.z -staging`、`sh build_deploy.sh x.y.z`、`sh deploy_latest.sh` |

## Suggested Release Flow
- 來源筆記建議：在 `staging` 測完並確認要發布後，從 `staging` 建立 `release/x.y.z` branch。
- 在 `release/x.y.z` 執行 `version-update` 固定版本號。
- 由 `release/x.y.z` 提 MR 到 `deploy`。
- `deploy` branch 僅執行 `deploy_tool.sh` 打包部署，不再修改版本號。
- 次佳做法：不建立 release branch 時，可在 `staging` 測完後執行 `version-update`，再由 `staging` 進入 `deploy`，`deploy` 只負責打包。

## Failure Modes
- 常見問題：在 `master` 太早更新版本號，可能導致尚未確認發布的內容被綁定版本。
- 預防方式：來源筆記建議等 `staging` 測完且確認發布後，再於 `release/x.y.z` 或 `staging` 固定版本。
- 常見問題：在 `deploy` 才更新版本號，會讓部署 branch 同時承擔版本決策與打包工作。
- 預防方式：來源筆記建議 `deploy` 只接受已固定版本的 release，並只執行打包部署。
- 常見問題：手動打包 `web-front` 時混入 `_deploy` 或 `node_module`。
- 預防方式：優先使用 `deploy_tool.sh`，或手動排除上述資料夾。
