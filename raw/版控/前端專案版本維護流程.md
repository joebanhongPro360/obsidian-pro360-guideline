## Frontend Project Version Maintenance

⚛️ Web App

- 舊流程
    
    利用 config/version.js 管理API_KEY的更新
    
    每當新功能發布時，會建立新的API_KEY，並同時對應之更新大/中版本號
    
    發布時：(use deploy_tool.sh)
    
    會在打包過程中補上小版本號，並以完整版本號進行打包
    
    (note: 打包後version.js會被更新完整版本號，但這個不commit，打包後環境部署時會用到)
    
    ```bash
    $ git checkout deploy
    $ git pull --recurse-submodules
    $ ./deploy_tool.sh 4.7.11
    ```
    
    ```bash
    #香港版本：(branch: hk_deploy)
    $ git checkout hk_deploy
    $ git submodule update --init --recursive
    $ git pull --recurse-submodules
    $ ./deploy_tool_hk.sh 4.7.11
    ```
    
- 新流程
    - 前端工程師發負責做 feature, bug, 做完發MR

⚛️ Web Front:

版本號紀錄於package.json

透過 npm version 更新版本號以及可帶入api-key

(僅大版本需更新API KEY)

```bash
$ npm run version-update major [NEW-API-KEY]
$ sh deploy_tool.sh
```

```bash
$ npm run version-update minor
$ sh deploy_tool.sh
```

```bash
$ npm run version-update patch
$ sh deploy_tool.sh
```

# 手動打包需排除 _deploy 及 node_module 兩個資料夾，使用 deploy_tool.sh 則自動排除

# **master merge 到 staging, staging 提 MR 到 deploy，在 deploy branch version-update 後使用 deploy_tool.sh 打包**

- 優化方向
    
    建議：**在 staging 測完、確認要發布後，從 staging 拉出 `release/x.y.z` 更新版本號**，再由 `release/x.y.z` 提 MR 到 `deploy`。
    
    不要在 `master` 太早更新，也不要在 `deploy` 才更新。
    
    比較適合你的流程：
    
    ```
    master → staging
    staging 測試確認發布內容
    staging → release/x.y.z
    在 release/x.y.z 跑 version-update
    release/x.y.z → deploy
    deploy 跑 deploy_tool.sh 打包部署
    ```
    
    這樣版本號會連續，而且時機也合理：
    
    - `master`：開發主線，不急著決定版本號
    - `staging`：整合測試，不一定每次都發布
    - `release/x.y.z`：確認要發布後才固定版本號
    - `deploy`：只接受已固定版本的 release，不再改版本
    
    你的 Note 可以改成：
    
    ```
    # master merge 到 staging 並完成測試後，確認發布內容與版本號。
    # 從 staging 建立 release/x.y.z branch，在 release branch 執行 version-update。
    # release/x.y.z 提 MR 到 deploy，deploy branch 僅執行 deploy_tool.sh 打包部署，不再修改版本號。
    ```
    
    如果你不想多一個 release branch，次佳做法是：
    
    ```
    master → staging
    在 staging 測完後執行 version-update
    staging → deploy
    deploy 只打包
    ```
    
    但我會更推薦 `release/x.y.z`，因為它可以避免 staging 還在繼續收其他改動時，影響已確認要發布的版本。
